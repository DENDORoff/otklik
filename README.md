# «Отклик» — система обратной связи и предложений сотрудников

Работающий MVP для хакатона ГК «Модус Трейд». Сотрудник подаёт проблему или идею,
система маршрутизирует обращение в профильный отдел, начальник назначает исполнителя,
автор видит итог и оценивает результат.

**Репозиторий:** https://github.com/DENDORoff/otklik · **Код:** [`otklik/`](otklik)

## EN summary

**Otklik** is an internal employee feedback system: an employee submits an issue or an
idea, the system routes it to the right department by a database rule, the head of the
department assigns an owner and a deadline, and the author sees the outcome and rates it.

- **Stack:** Next.js 15 (App Router) · React 19 · TypeScript 6 · Tailwind 3 · Prisma 6 ·
  PostgreSQL (Neon) in production, SQLite locally · Server Actions · zod · jose · bcryptjs
- **Roles:** employee / department head / administrator — every permission is checked on the
  server, not in the UI
- **Extras:** light & dark theme, RU/EN/KZ interface, public landing page with live stats,
  Bitrix24 integration module (disabled by default), legal & personal-data contour,
  SEO, accessibility (WCAG AA), security hardening
- **Data:** synthetic only — 7 departments, 24 users, 19 categories, 18 routing rules, 21 appeals

**Live demo:** https://otklik.deworld.su/ (Vercel + Neon PostgreSQL)

## Что умеет сервис

### Подача обращения

- **Мастер из трёх шагов** с прогрессом «Шаг N из 3»: тип и категория → описание → срок и отправка.
- **Категория «Другое»** — автор вводит свою формулировку, она хранится в `Appeal.customCategory`;
  такое обращение уходит в очередь «Неназначенные», администратор маршрутизирует его вручную.
- **Поиск похожих** — `/api/similar` подбирает до 4 доступных пользователю обращений по тексту,
  показывает их прямо в мастере и снижает количество дублей.
- **Проверка вложения** — размер, имя, MIME и сигнатура файла; исполняемые файлы запрещены.
- **Согласие** на обработку данных фиксируется версией и датой в профиле.

### Маршрутизация и назначение

- **Правило «категория → отдел» живёт в базе**, а не в коде: администратор меняет маршрут
  без релиза. «Не направлять» деактивирует правило.
- **Fallback-очередь**: нет правила → «Неназначенные» + уведомление администратору.
- **SLA по приоритету**: высокий — 3 дня, средний — 7, низкий — 14. Просрочка подсвечивается
  и собирается в отдельной вкладке списка.
- **Исполнителя назначает начальник отдела** (не автор) — как требует ТЗ.
- **Перенаправление** между отделами с лимитом 3 перехода; дальше — эскалация администратору.

### Работа по обращению

- **Жизненный цикл:** Новое → На рассмотрении → (Ожидает уточнения ↔ На рассмотрении) →
  В работе → Реализовано → Закрыто; альтернативы — Отклонено, Дубликат.
- **Уточнение автору** и **ответ автора** — с возвратом обращения в работу.
- **Возврат исполнителю начальнику** — с обязательным комментарием.
- **Мотивированный отказ** — причина видна автору и попадает в историю.
- **Итог и оценка 1–5** — оценка закрывает обращение и попадает в аналитику.
- **История событий**: кто, когда и что изменил — по каждому обращению.

### Список, поиск, выгрузка

- Вкладки **«Все / Мои / На мне / Просроченные»**, сворачиваемые фильтры (статус, категория,
  отдел, тип, приоритет, поиск по тексту), отдельный мобильный список.
- **CSV-выгрузка** с BOM и разделителем `;`, защитой от формул Excel и rate limit; учитывает права.

### Аналитика и улучшения

- Доля рассмотренных, доля с результатом, время первого ответа, среднее время решения,
  просрочка, средняя удовлетворённость, разрез по типам, категориям и статусам.
- Топ повторяющихся проблем (дубликаты по категориям).
- **Лента улучшений** `/improvements` — обезличенная: видно, что изменилось, но не кто пожаловался.

### Роли и администрирование

- Права проверяются **на сервере** (Server Actions), а не прятанием кнопок в интерфейсе.
- Админка: правила маршрутизации, справочники отделов/категорий/людей, очередь «Неназначенные»,
  обработка запросов по персональным данным, журнал безопасности.
- **Журнал безопасности**: входы, блокировки подбора пароля, создание обращений, смена правил,
  запросы по ПДн, события интеграций. Пароли и тексты обращений не записываются.

### Персональные данные

- `/data-request` — запрос на доступ, исправление, удаление или отзыв согласия.
- Обработка — в админке со сроком ответа до 10 рабочих дней; действия попадают в журнал.

## Как устроен процесс

```
Сотрудник                      Начальник отдела              Исполнитель            Администратор
     │                                  │                          │                      │
     ▼                                  ▼                          ▼                      ▼
подача (3 шага) ──▶ маршрутизация ──▶ назначение ──▶ работа ──▶ итог ──▶ оценка ──▶ закрытие
     │                 из БД            + срок SLA      │           │
     │                     │                          │           │
     └── нет правила ─────┴──▶ очередь «Неназначенные» ────────────┘
```

Маршрут обращения меняется **записью в базе**, а не изменением кода — это главная идея продукта:
«структура компании — это данные».

## Архитектура

| Слой | Технология | Почему |
|---|---|---|
| Фреймворк | Next.js 15 (App Router) | SSR и Server Actions в одном процессе |
| UI | React 19, Tailwind 3 | быстрый брендированный интерфейс, тёмная тема одной переменной |
| Язык | TypeScript 6 | типы на границах данных и действий (TS 7 несовместим с Next 15) |
| БД | SQLite + Prisma 6 | ноль настройки на демо-машине; переход на PostgreSQL — смена `DATABASE_URL` |
| Авторизация | `jose` (JWT) + `bcryptjs` | сессия в httpOnly-cookie, пароли — bcrypt |
| Валидация | zod | единые схемы для форм и API |
| Шрифты | Montserrat self-host (OFL) | без внешних запросов, лицензия позволяет публикацию |
| Аналитика | SQL-агрегаты Prisma + CSS-графики | без тяжёлых библиотек |

```
src/
├── app/
│   ├── (app)/          защищённые экраны: appeals, inbox, improvements, analytics, admin, settings…
│   ├── legal/          политики, согласие, cookie, возврата, лицензии
│   ├── api/            similar (похожие), export (CSV), integrations/bitrix24 (вебхук)
│   ├── page.tsx        публичный лендинг со статистикой
│   └── layout.tsx      корневой layout: тема, язык, cookie-баннер
├── components/         UI: мастер, карточка, действия, модалки, бейджи, оформление
└── lib/                auth, permissions, appeals, security, bitrix24, i18n, company, format
```

Решения, которые стоит знать:

- **Server Actions вместо REST** — права и валидация живут рядом с операцией; REST оставлен
  только там, где нужен файл или поток (CSV, JSON похожих, вебхук интеграции).
- **Маршрутизация в БД** — см. выше.
- **Тема — class-based** (`darkMode: "class"`), палитра в CSS-переменных: одна точка правки.
- **Язык — cookie + `Accept-Language`**, словари в `src/lib/i18n`, ключ = русская исходная строка,
  поэтому непереведённая строка остаётся читаемой, а не ломает интерфейс.
- **Клиенту отдаётся только нужная выборка переводов** — полные словари в бандл не попадают.

| Отдел | Сотрудников | Руководитель | Правил маршрутизации |
|---|---|---|---|
| Продажи | 3 | есть | 5 |
| Закупки | 2 | есть | 2 |

У каждого отдела есть руководитель и сотрудники. Категория «Другое» правила не имеет by design —
такие обращения идут в очередь «Неназначенные» для ручной маршрутизации. Техотдел и Сервис
получают обращения через перенаправление (сценарий «Продажи → IT-разработка»): правила для них
заводятся в админке, структура не зашита в код.

## Безопасность и юридический контур

- Пароли — bcrypt; сессия — JWT в httpOnly-cookie с `SameSite=Lax`; лимит входа 5 попыток / 15 минут.
- Rate limit на формы, поиск похожих и CSV; проверка загрузок (размер, имя, MIME, сигнатура).
- CSP без внешних скриптов, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`,
  `Permissions-Policy`, HSTS в production.
- Чужое обращение по прямой ссылке → 404 (брендированная страница), отладочные сведения не раскрываются.
- `.env`, `dev.db`, `node_modules`, `.next`, `storage/uploads` — вне Git.
- Политика конфиденциальности, согласие на обработку, условия использования, политика cookie,
  политика возврата, лицензии — плюс cookie-баннер и форма запроса на удаление данных.
- Все демо-реквизиты явно помечены: стенд нельзя спутать с реальной компанией.

## Интерфейс: темы, языки, доступность

- **Светлая и тёмная тема** с переключателем в разделе «Настройки» (плюс вариант «как в системе»):
  выбор запоминается (localStorage + cookie), тема применяется до первой отрисовки — вспышки нет;
  контраст проверен по WCAG AA в обеих темах.
- **Языки RU / EN / KZ**: переключатель в настройках, состояние в cookie,
  дата и числа форматируются по локали. Юридические документы опубликованы на русском.
- **Липкая шапка**: лого, навигация и меню профиля всегда на виду при прокрутке;
  уведомления, настройки и выход — в выпадающем списке профиля.
- **Настройки — отдельная кнопка** в шапке: имя сотрудника не является ссылкой на них.
- Доступность: skip-link, focus-visible, `aria`-атрибуты, alt-тексты, reduced-motion,
  контраст ≥ 4.5:1, клавиатурная навигация, ошибки рядом с полем.
- Иконки: один минималистичный контурный набор (`src/components/icons.tsx`) — навигация,
  заголовки разделов, основные действия и пустые состояния; рядом всегда текст.

### Где можно запустить

| Площадка | Подходит ли | Почему |
|---|---|---|
| **Vercel** | да, рекомендуется | Next.js из коробки, Server Actions, бесплатный тариф для демо |
| **Render / Railway / Fly.io** | да | обычный Node-процесс + PostgreSQL или диск с SQLite |
| **Свой VPS / контур компании** | да | полный контроль, нужен HTTPS и бэкапы |
| GitHub Pages | нет | Pages отдаёт только файлы и не запускает Node: Server Actions, база и сессии там не работают |

Приложение «Отклик» — не статический сайт: маршрутизация, авторизация и аналитика считаются
на сервере, поэтому для полного демо нужен Node-хостинг. Локально это SQLite
(`prisma/dev.db`), на сервере — PostgreSQL (смена одной строки `DATABASE_URL` и переменной
`DATABASE_PROVIDER`).

**Для Vercel всё подготовлено:** схема PostgreSQL (`prisma/schema.postgres.prisma`),
начальная миграция (`prisma/migrations/0_init`), генерация Prisma-клиента под нужного
провайдера в `postinstall`, адаптер хранилища вложений (Vercel Blob) и `vercel.json`.
Пошаговая инструкция и список того, что нужно от оператора — в
[`РАЗВЁРТЫВАНИЕ.md`](РАЗВЁРТЫВАНИЕ.md).

## Пути развития

Приоритеты — по ценности для компании и стоимости внедрения.

### Ближайший этап

| Направление | Что даст | Оценка |
|---|---|---|
| **Интеграция с Битрикс24** | обращение → задача ответственному в портале, статус возвращается обратно; модуль уже готов, нужен портал и вебхук | 1–2 недели вместе с настройкой портала |
| **Синхронизация справочников с 1С** | отделы и сотрудники перестают заводиться руками; оргструктура живёт в учётной системе | 2–3 недели |
| **Конструктор структуры** | отделы, категории и правила маршрутизации — в интерфейсе администратора, без правки кода | 2 недели |
| **Каналы уведомлений** | email (через SMTP/задачу), Telegram, корпоративный чат; сейчас только внутрисистемные, email имитируется | 1–2 недели на канал |
| **SSO и корпоративный каталог** | вход через Active Directory/LDAP, роли и отделы подтягиваются автоматически | 2 недели |

### Средний этап

| Направление | Что даст |
|---|---|
| **Анонимные обращения** | отдельный тип без персональных данных — для оценки идей, условий работы и обратной связи без страха |
| **Клиентская ОС / опросы** | регулярные пульс-опросы с привязкой к подразделению, агрегированные результаты |
| **Интеграция с почтой и мессенджерами** | сбор обращений из корпоративной почты и чатов |
| **Мобильное приложение или PWA** | подача обращения и статус с телефона, push-уведомления |
| **Публичный API** | программный доступ к обращениям для портала, Power BI и внешних систем |
| **Обогащение правил** | ML-подсказки категории и отдела по тексту обращения, автоподбор похожих по смыслу |
| **Расширенная аналитика** | когорты, динамика по отделам, выгрузка в BI, планирование нагрузки |

### Технические улучшения

- **PostgreSQL** вместо SQLite (один параметр `DATABASE_URL`) для пилота с реальной нагрузкой.
- **Фоновые задачи** (очередь) для отправки уведомлений и синхронизации с порталами.
- **Полнотекстовый поиск** (PostgreSQL FTS или внешний индекс) вместо `LIKE` по описанию.
- **WebSocket/SSE** для живого обновления статуса обращения у автора.
- **Кэш аналитики** (Redis) и выгрузка больших выборок в фоновое задание.

## Ограничения

Честно о границах демо-стенда:

- Уведомления только внутрисистемные; email-канал имитируется.
- Справочники меняются через сид; визуальный конструктор — этап 2.
- Интеграции с Битрикс24 и 1С описаны, модуль Битрикс24 собран, но в демо-стенде выключен.
- Юридические документы опубликованы на русском языке; интерфейс — на трёх языках.
- Данные синтетические: метрики на лендинге и в аналитике показывают поведение демо-набора,
  а не реальные показатели компании.
- Перед промышленной эксплуатацией нужны проверка текстов юристом, уведомление РКН,
  HTTPS, бэкапы и мониторинг.
