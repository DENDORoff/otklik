# Питч «Отклик» — вероятные вопросы жюри и ответы

Справочник для спикера и репетиции. Ответы сгруппированы по темам. Краткие версии есть на
слайде 16 презентации (`ПИТЧ-ПРЕЗЕНТАЦИЯ.pptx`), здесь — полные, с цифрами и источниками в
репозитории.

Проект — открытый репозиторий: **https://github.com/DENDORoff/otklik** · данные синтетические ·
пароль `demo1234` · как развернуть — [`РАЗВЁРТЫВАНИЕ.md`](РАЗВЁРТЫВАНИЕ.md).

---

## 1. Продукт и бизнес

### 1.1. Почему не хватает корпоративного чата или Google Forms?

Форма возвращает только ответ, чат — только переписку. Ни одно из них не даёт: владельца
обращения, срок (SLA по приоритету), историю «кто, что, когда», аналитику повторяющихся тем
и замкнутый цикл с оценкой автора. Наша система — это процесс: подача → маршрутизация →
начальник назначает исполнителя → итог → оценка → закрытие.

### 1.2. Чем мы отличаемся от Битрикс24 «Справочник → Задача»?

Битрикс24 — это система задач для исполнителей; она не решает проблему **обратной связи от
сотрудников**: она не привязывает обращение к категории компании, не маршрутизирует его по
правилам «категория → отдел», не считает дубликаты, не ждёт оценку автора. Мы — надстройка
над процессом: Битрикс может остаться каналом уведомления (модуль готов и проверен на
макете), но поток обращений живёт в «Отклике».

### 1.3. Кто наш пользователь и сколько их?

Все сотрудники — авторы; начальники 7 отделов — обработчики; администратор — владелец
структуры и правил. Демо показывает полный цикл на 24 синтетических пользователя по 7
отделам из датасета. В бою — от сотен до тысяч сотрудников; узкое место — не нагрузка, а
дисциплина сроков, поэтому продукт проектирует её вокруг себя (эскалация после 3
перенаправлений, уведомления, подсветка просрочки).

### 1.4. Какие метрики успеха для пилота?

- доля обращений, рассмотренных за SLA (цель ≥ 80%);
- время до первого ответа (цель ≤ 3 дней);
- время до решения по приоритету;
- удовлетворённость автора ≥ 4 из 5;
- главное — **число улучшений, доведённых до внедрения** (а не количество жалоб).

Источник — `КОНЦЕПЦИЯ.md` §7 и ТЗ п. 2.7.

### 1.5. Почему оценка 1–5 обязательна?

Обращение не закрывается без оценки автора — только так метрика удовлетворённости не
превращается в формальность. Оценка закрывает обращение, попадает в аналитику и помогает
начальнику увидеть системные сбои.

## 2. Технические решения

### 2.1. Какой стек и почему именно он?

| Слой | Технология | Причина |
|---|---|---|
| Фреймворк | Next.js 15 (App Router) + React 19 | Server Components + Server Actions: права и валидация на сервере, **без отдельного REST-слоя**; First Load JS ~103 кБ |
| Язык | TypeScript 6 | ошибки на этапе компиляции; TS 7 ломает цепочку Next 15 — намеренно не обновляем |
| БД | Prisma 6 | одна схема на SQLite (локальный стенд) и PostgreSQL (прод); переход — одной командой `db:push:pg` |
| Авторизация | jose (JWT httpOnly-cookie, sameSite=lax) + bcryptjs | ноль внешних сервисов, сессия подписана и ограничена 7 днями |
| Валидация | zod | на каждой форме и Server Action |
| Стили | Tailwind 3 + Montserrat (self-host, SIL OFL) | фирменный стиль ГК «Модус Трейд», без Google Fonts |
| Инфра | Vercel + PostgreSQL (например, Neon) | serverless-бэкенд; автодеплой из `main` |

Принцип: **один процесс, одна БД, ноль внешних сервисов на демо**. Никакой «платформы»
ради платформы.

### 2.2. Почему не Next 16 и Prisma 7 после аудита?

`npm audit fix --force` предлагал именно их — и мы сознательно отказались. Next 16 меняет
требования к сборке, Prisma 7 — генерацию клиента и `prisma.config`. При этом все три
уязвимости недостижимы из пользовательского ввода (см. 2.3). Мы закрыли корень точечными
`overrides` — стеки остались рабочими, аудит чист. Типичный ответ жюри: «меньше риска, чем
в большом рефакторинге перед защитой».

### 2.3. Что было в npm audit и как исправлено?

Было: **9 уязвимостей (8 высоких, 1 умеренная)**. Корней — три, все транзитивные:

| Пакет | Advisory | Почему не достижим из пользовательского ввода | Патч |
|---|---|---|---|
| `postcss` 8.4.31 (×4 advisory) | XSS в выводе CSS; чтение `.map` через `sourceMappingURL` | PostCSS в Next используется только в webpack-сборке на наших CSS; пользовательский CSS не загружается | `overrides: postcss ^8.5.32` |
| `deepmerge-ts` 7.1.5 | переполнение стека на рекурсивных объектах | только CLI Prisma; `prisma.config.ts` в проекте нет — ветка с мержем не выполняется | `overrides: deepmerge-ts ^8.0.2` |
| `zod` 4.1.11 | исчерпание памяти на больших коллекциях | `zod` валидирует локальный конфиг Vercel CLI; собственный `zod` приложения — 4.6.7 | `overrides: zod ^4.6.7` |

Итог: `npm audit` → **found 0 vulnerabilities**, мажорные версии Next / Prisma / React
не тронуты, CSS собран **байт-в-байт идентично** (тот же SHA-256). Полный разбор —
`ТЕХНИЧЕСКАЯ-КОНЦЕПЦИЯ.md` §7.1.

### 2.4. Почему «зависали» кнопки и что сделано?

Воспроизведено на стенде с неотвечающим server action. Две причины:

1. Server action уходит обычным `fetch` **без клиентского таймаута** — если ответа нет,
   React оставляет `useFormStatus().pending === true` бесконечно: кнопка блокируется с «…».
2. Особенность React 19: значение `pending` живёт в контексте перехода, и **любая
   перерисовка компонента вне этого перехода сбрасывает его в `false`** — индикатор может
   пропасть сам по себе.

Что сделано:

- **сторожевой таймер** `src/lib/pending-watchdog.ts`: через 20 с без ответа блокировка
  снимается, кнопка пишет «Сервер не ответил. Нажмите, чтобы повторить»; повторный клик
  перезапускает таймер;
- **таймаут запросов к базе 10 с** (`src/lib/db.ts`): недоступный/зависший запрос падает
  с понятной ошибкой `DbTimeoutError` → страница ошибки с кнопкой «Повторить»;
- индикация на всех действиях: «Входим…», «Выходим…», «Публикуем обращение…» + спиннер.

Тайминги проверены в браузере: 1.5 с — «Ждём…», 10.5 с — «Ждём…», 21.5 с — кнопка снова
активна. Подробности — `ИСТОРИЯ-РАБОТЫ.md` §20.

### 2.5. Как это масштабируется?

Чтение — по индексам (статус, автор, отдел, дедлайн). Серверная часть — stateless, сессия —
JWT в cookie, данные — PostgreSQL (serverless, ветки для pre-production). При росте:
(1) кэш на аналитику, (2) read-replica, (3) вынос уведомлений в очередь. Ни одна из этих
мер не требует переписывать модель — она уже в production-форме.

### 2.6. Почему данные в PostgreSQL, а не в файле?

SQLite — только для локального стенда. PostgreSQL — продакшн: ветки `production`/`preview`,
снапшоты, подключение из Vercel без секретов в коде. Миграция
`prisma/migrations/0_init` + сид `prisma/seed.js` поднимают ту же схему и те же данные,
что и локально. Поставщика PostgreSQL выбираете сами — Neon, Supabase, собственный сервер,
контур компании; инструкция — в `РАЗВЁРТЫВАНИЕ.md`.

### 2.7. Что с логированием и аудитом?

Все чувствительные действия пишутся в `AuditLog`: вход, создание обращения, смена правила,
запрос ПДн, перенаправление, дубликат. Журнал доступен только администратору; ошибки
журнала не ломают основной сценарий.

## 3. Демонстрация и данные

### 3.1. Почему данные синтетические?

Условия хакатона: реальные сведения компании использовать нельзя. Данные взяты из
предоставленного датасета: 7 отделов, 24 пользователя, 19 категорий, 18 правил
маршрутизации, 21 обращение, 51 запись истории, 12 уведомлений. Сид воспроизводится
командой `npm run db:reset`.

### 3.2. Что будет, если правило не найдено?

Обращение уходит в очередь **«Неназначенные»** + уведомление администратору. После 3
перенаправлений — принудительная эскалация админу. Обращение не теряется и не «зависает».

### 3.3. Что делает правило «Другое»?

Автор вводит свою формулировку, она хранится в `Appeal.customCategory`, постоянного правила
нет — обращение маршрутизируется администратором вручную.

### 3.4. Как работает SLA?

Дедлайн ставится при переводе в «В работе» по приоритету: высокий — 3 дня, средний — 7,
низкий — 14. Просрочка подсвечивается в списке и попадает в аналитику/эскалацию.

### 3.5. Можно ли продемонстрировать смену правил на лету?

Да: войти администратором → админка → правило маршрутизации категории → новое обращение
той же категории уходит в другой отдел. Это и есть ключевой бит демо — структура компании
меняется без изменения кода.

## 4. Персональные данные и право

### 4.1. Как обрабатываются персональные данные?

В демо — только синтетические данные. В бою: вход по учётным записям компании, согласие на
обработку (`User.consentVersion/consentAt`), запросы на доступ и удаление (`/data-request`),
обработка запроса в админке со статусом «Обработан», журнал запроса. Политики,
`legal/privacy`, cookie-баннер — в приложении. Действия: HTTPS, бэкапы, уведомление РКН,
назначенный ответственный по ПДн.

### 4.2. Что сделать перед промышленной эксплуатацией?

1. Проверка текстов юриста (политики, согласие, оферта).
2. Уведомление в Роскомнадзор + назначение ответственного.
3. HTTPS + бэкапы базы данных + мониторинг (Sentry, UptimeRobot).
4. Уведомления по email — реальный провайдер (очередь уже пишется в БД).

## 5. Внедрение и риски

### 5.1. Сколько стоит внедрение?

Пилот — 4 недели в одном отделе («Закупки»), инфраструктура — любой управляемый PostgreSQL
(Neon входит в бесплатный тариф) и бесплатные лицензии (MIT для библиотек, SIL OFL для
Montserrat). Основная цена — время руководителей отделов и один администратор системы (~0.1 FTE).

### 5.2. Что мешает запуск завтра?

Юридический контур (политики и ПДн) и email-канал. Технически всё готово: авторизация,
роли, правила, отчёты. Внедрение — организационное, а не технологическое.

### 5.3. Риски и как их снимаем?

| Риск | Мера |
|---|---|
| Сотрудники перестанут писать | оценка автора + видимый итог: «моё обращение довели» — лучший стимул |
| Руководители игнорируют входящие | эскалация после 3 перенаправлений, подсветка просрочки, отчётность по отделу |
| Дубликаты заваливают очередь | подсказка похожих при создании + счётчик дубликатов по категориям |
| Утечка ПДн | только синтетические данные на демо; в бою — согласия, журнал, HTTPS, бэкапы |
| Зависание загрузок | сторожевой таймер 20 с + таймаут БД 10 с + страница «Повторить» |

## 6. Коммерциализация и масштабирование

### 6.1. Это продукт или внутренний инструмент?

Внутренний инструмент ГК «Модус Трейд», построенный на открытом стеке. Его можно
тиражировать в другие компании группы и заменить email/чаты единой точкой обратной связи.

### 6.2. Что дальше после пилота?

Конструктор орг-структуры (директория отделов и версии правил), интеграции Битрикс24/1С,
ML: автокатегоризация и поиск похожих, опросы и NPS. Всё это — следствие того, что
структура компании у нас — данные, а не код.

## 7. Процесс и качество

### 7.1. Что проверено?

Полный чек-лист — `ЧЕК-ЛИСТ_ТЗ.md` и раздел «Что проверено» в `ОТЧЁТ.md`. Ключевое:
сборка без ошибок; 0 уязвимостей; сквозной сценарий (принять → назначить → выполнить →
оценить → закрыть); 404 на чужое обращение; WCAG 2.1 AA (0 нарушений на 10 страницах ×
2 темы); 418 px без горизонтального скролла; индикация загрузки на всех действиях;
воспроизведённый и закрытый «зависающий» кейс.

### 7.2. Что будет с проектом после хакатона?

Хакатон завершён: демо-стенд (Vercel + PostgreSQL) выведен из эксплуатации, репозиторий
оставлен как портфолио (`github.com/DENDORoff/otklik`). В нём — вся документация,
история решений и полная инструкция повторного развёртывания (`РАЗВЁРТЫВАНИЕ.md`).
Команда готова сопровождать пилот.
