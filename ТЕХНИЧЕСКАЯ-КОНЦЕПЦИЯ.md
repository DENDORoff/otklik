# Техническая концепция «Отклик»

Документ описывает архитектуру, данные, безопасность, развёртывание и развитие MVP.
Продуктовая часть, роли и жизненный цикл — в [`КОНЦЕПЦИЯ.md`](КОНЦЕПЦИЯ.md),
итоги проверки — в [`ОТЧЁТ.md`](ОТЧЁТ.md).

---

## 1. Цели и ограничения

**Цель MVP** — доказать, что сквозной процесс обратной связи работает end-to-end:
подача → маршрутизация → назначение → выполнение → итог → оценка → закрытие.

**Ограничения:**

- только синтетические данные датасета;
- интеграции Битрикс24 / 1С — только описание;
- один сервер, SQLite, без внешних сервисов;
- демо должно разворачиваться на ноутбуке за минуты.

---

## 2. Архитектура

```
Браузер
  │  HTML / RSC / Server Actions
  ▼
Next.js 15 (App Router, React 19, TypeScript 6)
  ├─ Server Components  — чтение данных, проверка прав
  ├─ Server Actions     — мутации, валидация, аудит
  ├─ Route Handlers     — /api/similar, /api/export/appeals
  └─ Client Components  — мастер, модалки, фильтры, cookie-баннер
        │
        ▼
Prisma 6 ── SQLite (dev.db)
        │
        └─ storage/uploads (вложения)
```

**Почему Server Actions, а не REST:** меньше кода, проверка прав и валидация рядом
с операцией, нет отдельного слоя сериализации. REST-роуты оставлены только там, где
нужен файл или поток данных (CSV, JSON похожих).

**Рендеринг:** защищённые экраны — динамические (`ƒ`), публичные юридические страницы,
`sitemap.xml`, `robots.txt` и OG-изображение — статические (`○`).

## 3. Стек и обоснование

| Слой | Технология | Причина |
|---|---|---|
| Фреймворк | Next.js 15 App Router | SSR + Server Actions в одном процессе |
| UI | React 19, Tailwind 3 | быстрый брендированный интерфейс |
| Язык | TypeScript 6 | типы на границах данных и действий; TS 7 несовместим с Next 15 |
| БД | SQLite + Prisma 6 | нулевая настройка; смена провайдера одной строкой |
| Авторизация | `jose` (JWT) + `bcryptjs` | без внешнего провайдера |
| Валидация | zod | единые схемы для форм и API |
| Шрифты | Montserrat self-host (OFL) | без внешних запросов, лицензия позволяет |
| Аналитика | SQL-агрегаты Prisma | без тяжёлых библиотек |

## 4. Модель данных

Основные сущности (`otklik/prisma/schema.prisma`):

| Модель | Назначение |
|---|---|
| `Department` | отдел, начальник, сотрудники, обращения |
| `User` | сотрудник/начальник/админ, согласие, настройки уведомлений |
| `Category` | категория обращения, активность |
| `RoutingRule` | правило «категория → отдел», вес, активность |
| `Appeal` | обращение: тип, приоритет, статус, сроки, итог, `customCategory` |
| `AppealHistory` | события жизненного цикла: кто, что, когда |
| `Comment` | комментарии и ответы на уточнения |
| `Notification` | внутрисистемные уведомления |
| `Attachment` | вложение: имя, путь, MIME, размер |
| `AppealSubscription` | подписка автора на оригинал дубликата |
| `DataRequest` | запрос по персональным данным |
| `AuditLog` | журнал безопасности |

**Ключевые решения:**

- SQLite не поддерживает enum — статусы, типы, приоритеты и роли хранятся строками,
  константы и подписи — в `src/lib/constants.ts`.
- Одно активное правило на категорию; «Не направлять» деактивирует правило.
- «Другое» — категория без правила; авторская формулировка — в `Appeal.customCategory`.
- Согласие фиксируется версией и датой в `User`, а не отдельной таблицей — для MVP достаточно.
- Аудит хранит действие, пользователя, почту, IP и метаданные; тексты обращений и пароли
  не пишутся.

## 5. Права и роли

| Действие | Сотрудник | Начальник отдела | Админ |
|---|---|---|---|
| Создать обращение | да | да | да |
| Видеть свои | да | да | да |
| Видеть отдел | — | да | да |
| Видеть все | — | — | да |
| Назначить исполнителя | — | да, по своему отделу | да |
| Запросить уточнение | — | да | да |
| Отклонить / дубликат / перенаправить | — | да | да |
| Оценить и закрыть | автор | — | — |
| Правила маршрутизации | — | — | да |
| Запросы ПДн и журнал | — | — | да |

Проверка выполняется **на сервере** в каждом Server Action и в выборках
(`visibleWhere`), а не только скрытием кнопок. Чужое обращение по прямой ссылке → 404.

## 6. Основные сценарии реализации

### 6.1. Создание обращения

1. Мастер на клиенте собирает тип, категорию, описание, приоритет, файл и согласие.
2. Server Action `createAppeal`: rate limit 10/час → zod → категория («Другое» через
   upsert) → поиск активного правила → создание обращения и истории → согласие →
   проверка файла (имя, MIME, сигнатура, 5 МБ) → уведомления → аудит → redirect.
3. Нет правила или «Другое» → `departmentId = null`, уведомление всем админам,
   очередь «Неназначенные».

### 6.2. Маршрутизация и SLA

- Правило ищется по `categoryId`, активное, с максимальным весом.
- Ответственный — начальник отдела-получателя.
- Дедлайн ставится при переводе в работу: high 3 / mid 7 / low 14 дней.
- Просрочка вычисляется сравнением дедлайна с текущей датой и статусом.

### 6.3. Жизненный цикл

Переходы описаны в `src/app/(app)/appeals/[id]/actions.ts`. Каждый переход:

- проверяет роль и текущий статус;
- пишет событие в `AppealHistory`;
- создаёт уведомления;
- фиксирует `firstResponseAt`, `resolvedAt`, `closedAt`, `redirectCount` при необходимости.

Лимит перенаправлений — 3, далее уведомление администратору. Оценка 1–5 закрывает
обращение и участвует в аналитике.

### 6.4. Похожие обращения

`GET /api/similar?q=...` — только для авторизованных, rate limit 40/мин, минимум 12
символов, не более 4 результатов, выборка ограничена `visibleWhere`. Возвращает номер,
статус, категорию и короткий фрагмент.

### 6.5. CSV-выгрузка

`GET /api/export/appeals` — права через `buildListWhere`, rate limit 6/10 минут,
BOM для Excel, разделитель `;`, экранирование кавычек и защита от формул
(`=`, `+`, `-`, `@`).

## 7. Безопасность

| Угроза | Мера |
|---|---|
| Подбор пароля | bcrypt, лимит 5 попыток / 15 минут, аудит блокировок |
| Кража сессии | httpOnly + sameSite cookie, подписанный JWT, срок 7 дней |
| Подделка запросов | Server Actions + проверка Origin, `form-action 'self'` |
| XSS | React-экранирование, CSP без внешних скриптов |
| SQL-инъекции | параметризованные запросы Prisma |
| Небезопасные файлы | проверка размера, имени, MIME и сигнатуры; запрет скриптов |
| Обход прав | серверные проверки в каждом действии и выборке |
| Утечка секретов | `.env` вне Git, `AUTH_SECRET` обязателен в production |
| Кликджекинг | `X-Frame-Options: DENY`, `frame-ancestors 'none'` |
| MIME-sniffing | `X-Content-Type-Options: nosniff` |
| Спам формами | rate limit по пользователю и IP |
| Отладка в production | `poweredByHeader: false`, стандартные ошибки Next |

Дополнительно: аудит входов, созданий, изменений правил и запросов ПДн; журнал доступен
только администратору. Для реального запуска — HTTPS, резервное копирование, уведомление
РКН, назначение ответственного за ПДн.

## 8. Производительность

- Server Components уменьшают клиентский JS; First Load JS ~103–111 kB на маршрут.
- Шрифты self-host с `font-display: swap`, только два subset (cyrillic, latin).
- Нет внешних SDK, аналитики и рекламных пикселей.
- Скелетоны и Suspense вместо блокирующих спиннеров.
- Индексы Prisma для частых выборок (статус, автор, отдел, дедлайн).
- OG-изображение и юридические страницы статические.

## 9. Развёртывание

**Демо-стенд:**

```powershell
npm.cmd install
npm.cmd run db:push
npm.cmd run db:seed
npm.cmd run build
npm.cmd run start -- --port 3000
```

**Пилот:**

- PostgreSQL — заменить `provider` и `DATABASE_URL`, прогнать миграции;
- reverse proxy с HTTPS (Caddy/Nginx), HSTS уже отдаётся приложением;
- `AUTH_SECRET` — случайная строка ≥ 32 символов;
- файлы вложений — объектное хранилище или отдельный том;
- резервное копирование БД и журналов;
- мониторинг ошибок и доступности.

## 11. План развития

1. **MVP (сделано)** — сквозной процесс, роли, SLA, аналитика, юридический контур.
2. **Ближайшее** — визуальный конструктор отделов и категорий, экспорт PDF,
   самостоятельное удаление аккаунта, резервный скринкаст.
3. **Интеграции** — Битрикс24, 1С, почтовый провайдер.
4. **Аналитика 2.0** — семантический поиск похожих, ML-категоризация, прогноз просрочки.
5. **Клиентская ОС и опросы** — NPS, пульс-опросы, внешние обращения.

## 12. Тестирование

- Сборка `npm run build` — типы и линт.
- Ручные сквозные сценарии по ролям (см. `ОТЧЁТ.md` §3).
- Проверка прав прямыми ссылками.
- Проверка загрузок: допустимые и запрещённые файлы.
- Проверка rate limit и блокировки входа.
- Проверка мобильной ширины и отсутствия горизонтального скролла.
- Проверка заголовков безопасности и `robots.txt` / `sitemap.xml`.
- Автотестов в MVP нет — это осознанное ограничение; приоритет отдан сквозному демо.
