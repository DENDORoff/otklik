# Интеграция «Отклик» ↔ облачный портал Битрикс24

Документ описывает модуль интеграции с облачным порталом Битрикс24, реализованный
в MVP системы обратной связи «Отклик». Модуль **выключен по умолчанию**: без
переменных окружения приложение работает как обычно, ни один вызов в портал не
уходит, ошибок нет.

> Демонстрационный стенд. Реальные данные компании в портал не передаются и в
> репозитории не хранятся. Портал, токен и секрет — только синтетические.

---

## 1. Зачем нужна интеграция

«Отклик» живёт внутри компании и хорошо работает как система обратной связи:
подача → маршрутизация → назначение исполнителя → итог → оценка автора.

Исполнители, однако, работают в облачном портале: задачи, сроки, обсуждения и
статусы там. Без интеграции сотруднику приходится дублировать одну и ту же
работу в двух системах, а руководителю — сверять их вручную.

Интеграция решает три задачи:

| Задача | Что делает модуль |
|---|---|
| Не терять обращения | Обращение превращается в задачу ответственному в портале — с ним невозможно не заметить |
| Единый статус | Статус задачи в портале возвращается в «Отклик» (выполнена / прокомментирована) |
| Прозрачность для автора | Автор видит, что по его обращению реально делают, и получает уведомление |

Интеграция **односторонне синхронизирует рабочую нагрузку** и **получает обратно
статус выполнения**. Это не замена «Отклику»: учёт обращений, оценки, SLA и
аналитика остаются в «Отклике».

---

## 2. Что синхронизируется

### 2.1 Исходящая синхронизация (Отклик → портал)

| Событие в «Отклике» | Действие в портале | Метод REST |
|---|---|---|
| Назначен исполнитель (`assignAppeal`) | Создаётся задача: название, описание, срок, ответственный | `tasks.task.add` |
| Повторное назначение | Обновляются ответственный и срок, добавляется комментарий | `tasks.task.update` + `tasks.task.addComment` |
| Обращение реализовано | Задача завершается с текстом итога | `tasks.task.complete` (+ комментарий) |
| Обращение отклонено | Задача завершается с причиной отказа | `tasks.task.complete` |
| Обращение возвращено начальнику | Задача остаётся открытой, добавляется комментарий | `tasks.task.update` + `tasks.task.addComment` |
| Обращение передано в другой отдел / помечено дубликатом | Задача завершается с пояснением | `tasks.task.complete` |

В обращении сохраняются `Appeal.bitrixTaskId` и `Appeal.bitrixTaskUrl` — по ним
обращение находится при обратном событии, а сотрудник видит прямую ссылку на
задачу в карточке обращения.

Ответственный в портале определяется по рабочему e-mail сотрудника: вызов
`user.get` с фильтром `EMAIL`, ответ кэшируется в памяти процесса на 10 минут.
Если сотрудник в портале не найден, задача всё равно создаётся (без
ответственного), а в журнал безопасности пишется запись
`bitrix24.task_created` с `responsibleResolved: false`.

### 2.2 Входящая синхронизация (портал → Отклик)

Обрабатываются два события:

| Событие портала | Действие в «Отклике» |
|---|---|
| Задача прокомментирована (`ON_TASK_COMMENT_ADD`) | Комментарий из портала попадает в комментарии обращения, в историю и автору уходит уведомление |
| Задача выполнена (`ON_TASK_COMPLETE`) | Обращение переводится из «В работе» в «Реализовано», фиксируется итог, автор получает уведомление |

Обращение находится по `Appeal.bitrixTaskId`. Если задача в портале не найдена в
«Отклике» — событие игнорируется (ответ `200`, запись в журнал), данные не
создаются.

Комментарий из портала подписывается исполнителем обращения (исполнитель →
ответственный → администратор), так как в «Отклике» автором комментария всегда
должен быть сотрудник.

## 3. Какие данные передаются

В портал уходит **минимально необходимый** набор:

| Поле | Пример | Зачем |
|---|---|---|
| Код обращения | `A-002` | Связь между системами |
| Категория | `Информационная прозрачность` | Понимание задачи без чтения внутренней системы |
| Приоритет | `средний` | Приоритет в портале (`fields[priority]`) |
| Срок | `2026-11-19` | Дедлайн задачи (`fields[deadline]`) |
| Текст обращения | до 800 символов | Существо задачи (иначе исполнитель не поймёт, что делать) |
| Ссылка обратно | `http://<host>/appeals/<id>` | Быстрый переход к полному контексту |
| ФИО/почта исполнителя | `sales@otklik.local` | Только для поиска ID сотрудника в портале (`user.get`), в саму задачу не попадает |

**Не передаются:** имя и почта автора обращения, персональные данные третьих
лиц, файлы-вложения, переписка по другим обращениям, история системы, учётные
данные, оценки авторов.

В портал не уходят и внутренние идентификаторы «Отклика», кроме ID обращения в
ссылке. Секреты (токен вебхука, `BITRIX24_INTEGRATION_SECRET`) в портал не
отправляются — токен является частью адреса и передаётся только по HTTPS.

## 4. Схема REST-вызовов

Базовый адрес: `https://<portal>/rest/1/<токен>/<метод>`, `POST`, тело — JSON.

### 4.1 Создание задачи

```http
POST https://portal.example.kz/rest/1/<токен>/tasks.task.add
Content-Type: application/json

{
  "fields[title]": "Отклик A-002: Информационная прозрачность",
  "fields[description]": "Обращение A-002 · категория «Информационная прозрачность»\nПриоритет: средний\nСрок: 19.11.2026\n\n<текст обращения>\n\nОткрыть в «Отклике»: http://localhost:3000/appeals/<id>",
  "fields[responsibleId]": "42",
  "fields[deadline]": "2026-11-19T18:00:00"
}
```

Ответ: `{"task": {"id": "759", ...}}` — `id` сохраняется в `Appeal.bitrixTaskId`.

### 4.2 Обновление задачи

```http
POST .../tasks.task.update
{"taskId": "759", "fields[status]": 2, "fields[deadline]": "2026-11-19T18:00:00"}
```

### 4.3 Завершение задачи

```http
POST .../tasks.task.complete
{"taskId": "759"}
```

Комментарий к задаче добавляется отдельным вызовом:

```http
POST .../tasks.task.addComment
{"taskId": "759", "text": "Обращение A-002 реализовано. Итог: ..."}
```

### 4.4 Поиск сотрудника и чтение задачи

```http
POST .../user.get
{"FILTER": {"EMAIL": "sales@otklik.local"}}
→ {"result": [{"ID": "42", "NAME": "...", "EMAIL": "..."}]}

POST .../tasks.task.get
{"taskId": "759"}
→ {"task": {"id": "759", "title": "...", "status": 5}}
```

### 4.5 Формат ошибок

Портал возвращает `{"error": "CODE", "error_description": "..."}`. Клиент
(`src/lib/bitrix24.ts`) разбирает эту форму и превращает в `Bitrix24Error` с
кодом и **очищенным** описанием. Отдельно обрабатываются:

| Код | Смысл | Реакция |
|---|---|---|
| `QUERY_LIMIT_EXCEEDED` | Превышен лимит запросов портала | Ошибка в журнал, основной сценарий не ломается |
| `ERROR_METHOD_NOT_FOUND` | Нет метода (например, `addComment` в старой редакции) | Одна попытка запасным именем `task.addComment` |
| `ACCESS_DENIED` / `ERROR_ACCESS_DENIED` | Не хватает прав вебхука | Ошибка в журнал `bitrix24.sync_failed` |
| HTTP ≠ 200 | Портал недоступен | `Bitrix24Error` с кодом `HTTP_<код>` |
| Превышен таймаут | Портал не ответил за `BITRIX24_TIMEOUT_MS` | `Bitrix24Error` с кодом `TIMEOUT` |

## 5. Настройка

### 5.1 Переменные окружения

Файл `otklik/.env` (образец — `otklik/.env.example`):

```dotenv
# Адрес входящего вебхука портала. Токен — часть URL, значение считается секретом.
BITRIX24_WEBHOOK_URL="https://portal.example.kz/rest/1/xxxxxxxxxxxxxxxx/"
# Идентификатор портала — показывается в карточке админки.
BITRIX24_PORTAL_ID="demo-portal"
# Общий секрет для входящих вебхуков (заголовок x-otklik-secret или поле secret).
BITRIX24_INTEGRATION_SECRET="длинная-случайная-строка"
# Таймаут вызова портала, мс (по умолчанию 8000, максимум 30000).
BITRIX24_TIMEOUT_MS="8000"
```

`.env` не коммитится. Значение `BITRIX24_WEBHOOK_URL` содержит токен портала —
его нельзя выводить в логи, в ответы API и в клиентский код.

### 5.2 Входящий вебхук в портале

В портале Битрикс24: **Разработчикам → Другое → Вебхуки** (в новых редакциях —
**Автоматизация → Сценарии → Вебхуки**).

1. Создать вебхук типа «входящий» (oncoming webhook) с адресом:
   `https://<адрес-«Отклика»>/api/integrations/bitrix24`.
2. В поле «Секрет» (или заголовке) указать то же значение, что и
   `BITRIX24_INTEGRATION_SECRET`. Модуль проверяет заголовок `x-otklik-secret`
   и, если его нет, поле `secret` (или `token`) в теле запроса.
3. Подписать вебхук на события задач: «задача добавлена/изменена/закрыта»,
   «добавлен комментарий к задаче» — точные имена событий (`ON_TASK_COMPLETE`,
   `ON_TASK_COMMENT_ADD`) зависят от редакции портала и уточняются у компании.
4. Адрес «Отклика» должен быть доступен из интернета по HTTPS и не закрыт
   аутентификацией (аутентификация — общий секрет внутри запроса).

Проверка вручную (PowerShell):

```powershell
$h = @{ "x-otklik-secret" = "<ваш секрет>" }
$b = '{"event":"ON_TASK_COMPLETE","data":{"task":{"id":"759"},"comment":{"text":"Готово"}}}'
[System.Text.Encoding]::UTF8.GetBytes($b) | Out-Null
Invoke-WebRequest -Uri "http://localhost:3000/api/integrations/bitrix24" `
  -Method POST -Body ([System.Text.Encoding]::UTF8.GetBytes($b)) `
  -ContentType "application/json; charset=utf-8" -Headers $h
```

Ожидаемый ответ: `{"ok":true,"matched":true,"applied":true,"appealCode":"A-002"}`.

Ответы маршрута:

| Код | Когда |
|---|---|
| `200` | Событие принято (в т. ч. `ignored: true` — неподдерживаемое событие) |
| `401` | Неверный или отсутствующий секрет |
| `404` | Интеграция выключена (нет `BITRIX24_WEBHOOK_URL`) |
| `429` | Превышен лимит запросов к маршруту (60 в минуту с одного IP) |
| `500` | Не удалось применить событие (подробности — в журнале безопасности) |

### 5.3 Карточка в админке

`src/components/bitrix24-card.tsx` показывает состояние подключения, портал,
число обращений с привязанной задачей и результат последней проверки связи.
Кнопка «Проверить соединение» выполняет один read-only вызов `user.current` и
пишет результат в журнал безопасности. Карточка встраивается в
`src/app/(app)/admin/page.tsx`.

## 6. Что нужно уточнить у компании

| Вопрос | Почему это важно | Что прислать |
|---|---|---|
| Точные имена событий вебхука | От них зависит разбор входящего запроса | Список событий портала по задачам (скриншот/выгрузка) |
| Формат тела вебхука | Структура `data.task`, `data.comment` различается | Пример JSON-полезной нагрузки |
| Права вебхука | Нужны методы `tasks.task.*` и `user.get` | Скриншот прав входящего вебхука |
| Имя и формат вебхука в портале | Влияет на маршрутизацию событий | Правило настройки вебхуков в портале |
| Поля задачи | Возможно, у задачи есть свои обязательные поля | Список полей типа задачи в портале |
| Часовой пояс портала | Сроки SLA и дедлайны задач должны совпадать | Часовой пояс портала и правило пересчёта |
| Идентификатор портала | Показывается в админке как «Портал» | ID или название портала |
| Проект/группа для задач | Задачи могут жить в отдельном проекте | ID проекта, если нужен |
| Политика хранения данных | Кто и как долго хранит тексты обращений в портале | Регламент и срок хранения |

## 7. Ограничения и риски

### 7.1 Идемпотентность

| Ситуация | Поведение |
|---|---|
| Повторная доставка одного вебхука | Статус не меняется повторно; комментарий не дублируется (поиск совпадающего текста за последние 15 минут) |
| Повторное назначение исполнителя | Задача не создаётся заново — обновляются ответственный и срок |
| Задача в портале закрыта дважды | Второй вызов возвращает ошибку портала — она пишется в журнал и **не** ломает сценарий «Отклика» |
| Обращение уже не «В работе» | Событие «выполнено» не меняет статус, но комментарий сохраняется |

### 7.2 Ретраи

Автоматических ретраев внутри «Отклика» нет: сбой портала фиксируется в журнале
и не повторяется автоматически, чтобы не плодить дубли в портале. Восстановление
— ручное: повторное назначение исполнителя обновляет существующую задачу.
Сторону портала (повторная доставка вебхука) обрабатывает дедупликация выше.

### 7.3 Лимиты портала

У Bitrix24 есть лимиты на частоту вызовов REST (приблизительно 20 запросов в
секунду на вебхук, при превышении — `QUERY_LIMIT_EXCEEDED`) и лимиты на
создание задач. «Отклик» делает единичные вызовы на каждое действие, поэтому
лимиты не достигаются; при пилотной нагрузке (десятки обращений в день)
запас большой. При необходимости — пакетная обработка через `batch` и очередь.

### 7.4 Прочие риски

| Риск | Митигация |
|---|---|
| Утечка токена вебхука | Токен не пишется в логи и ответы; ошибки очищаются функцией `sanitizeSecret` |
| Спам в вебхук | Обязательная проверка секрета (сравнение постоянного времени) + лимит 60 запросов в минуту с IP |
| Портал недоступен во время работы сотрудника | Любая ошибка портала перехватывается, пишется в журнал безопасности и не блокирует основной сценарий |
| Расхождение статусов двух систем | «Отклик» — источник истины по учёту; статус из портала применяется только к обращениям в состоянии «В работе» |
| Порочный круг (задача → вебхук → задача) | Из вебхука портал не вызывается никогда; неизвестные события игнорируются |
| Персональные данные в портале | Передаётся минимум; ПДн автора не уходят; согласие и порядок обработки — в политике конфиденциальности |

## 8. План пилота

**Шаг 1. Подготовка (1 день).** Компания выдаёт тестовый портал (или вебхук с
минимальными правами на синтетическом стенде), секрет и список событий. Секреты
задаются в `.env` на демо-машине, портал остаётся тестовым.

**Шаг 2. Проверка исходящей синхронизации (0,5 дня).** Назначение исполнителя
на синтетическом обращении → в портале появляется задача с корректным
названием, сроком и ответственным; в карточке обращения работает ссылка
«открыть в Битрикс24»; в журнале безопасности есть запись
`bitrix24.task_created`.

**Шаг 3. Проверка входящей синхронизации (0,5 дня).** Комментарий и завершение
задачи в портале → комментарий и статус «Реализовано» в «Отклике», уведомление
автору; повторная отправка события не дублирует данные; запрос без секрета
даёт 401.

**Шаг 4. Нагрузка и надёжность (0,5 дня).** Проверка таймаута и недоступности
портала: приложение продолжает работать, в журнале видны записи
`bitrix24.sync_failed`. Проверка дедупликации вебхуков.

**Шаг 5. Роли и доступ (0,5 дня).** Назначение исполнителя остаётся за
начальником отдела; администратор видит карточку интеграции и может
проверить соединение; рядовой сотрудник не видит настроек портала.

**Шаг 6. Решение о продукте (0,5 дня).** По итогам пилота решается: расширять
ли синхронизацию (согласования, комментарии без задачи, напоминания), нужны ли
дополнительные поля задачи, требуется ли очередь повторных попыток.

**Объём пилота:** 10–15 синтетических обращений, 1 отдел, 1 портал, 1 неделя.

## 9. Карта кода

| Файл | Назначение |
|---|---|
| `otklik/src/lib/bitrix24.ts` | Клиент портала: конфигурация, вызовы REST, создание/обновление/завершение задачи, очистка секретов |
| `otklik/src/app/(app)/appeals/[id]/actions.ts` | Исходящая синхронизация: создание задачи при назначении, обновление при смене статуса |
| `otklik/src/app/api/integrations/bitrix24/route.ts` | Входящий вебхук: проверка секрета, разбор события, комментарий и смена статуса |
| `otklik/src/components/bitrix24-card.tsx` | Карточка интеграции в админке |
| `otklik/src/app/(app)/admin/bitrix24-actions.ts` | Server action «Проверить соединение» |
| `otklik/prisma/schema.prisma` | Поля `Appeal.bitrixTaskId`, `Appeal.bitrixTaskUrl` и индекс по ним |

Журнал событий интеграции — таблица `AuditLog`, действия с префиксом
`bitrix24.`: `task_created`, `task_updated`, `task_completed`, `sync_failed`,
`webhook_applied`, `webhook_ignored`, `webhook_unmatched`, `webhook_unauthorized`,
`webhook_failed`, `connection_check`. Секреты в журнал не пишутся.
